Sebelum solution bisa dipakai, **platform admin** mendaftarkannya ke platform. Setiap langkah di halaman ini
bisa dilakukan lewat **console** (UI) atau **API**; keduanya memberi hasil yang sama. Semua endpoint di
halaman ini butuh token user platform admin, kecuali sinkronisasi permission yang dijalankan backend
solution dengan token service.

## Ringkasan alur

| # | Langkah | Dilakukan oleh | Console | API |
|---|---|---|---|---|
| 1 | [Buat solution](#_1-buat-solution) | Platform admin | **Platform → Solutions** | `POST /api/v1/solutions` |
| 2 | [Buat solution client](#_2-buat-solution-client) | Platform admin | Solution → tab **Client** | `POST /api/v1/solutions/{solutionId}/clients` |
| 3 | [Sinkronisasi permission](#_3-sinkronisasi-permission) | Backend solution | Tab **Permission** (hanya-baca) | `PUT /api/v1/solutions/{solutionId}/permissions/sync` |
| 4 | [Siapkan role global](#_4-siapkan-role-global-opsional) (opsional) | Platform admin | Solution → tab **Role global** | `POST /api/v1/solutions/{solutionId}/roles` |

Contoh di halaman ini mendaftarkan solution **Kasir Pintar** (kode `kasir-pintar`). Setelah selesai,
lanjutkan ke [Onboarding company](/docs/onboarding-company) agar pelanggan bisa memakai solution tersebut.

## 1. Buat solution

### Lewat console

1. Masuk ke console sebagai platform admin, lalu buka **Platform → Solutions** di sidebar.

   ![Menu Solutions di sidebar console](/images/docs/onboarding-solution/01-menu.png)

2. Klik **Buat solution** di kanan atas.

   ![Halaman daftar solution](/images/docs/onboarding-solution/02-list.png)

3. Isi **Nama**. **Kode** terisi otomatis dari nama (huruf kecil, angka, dan tanda hubung). Periksa kodenya
   sebelum menyimpan karena kode **tidak bisa diubah** lagi. **Deskripsi** boleh dikosongkan. Klik
   **Buat solution**.

   ![Form buat solution](/images/docs/onboarding-solution/03-create.png)

4. Console membuka halaman solution. Tab **Ringkasan** menampilkan **Kode (audience)**, status, dan versi
   katalog permission (masih `belum sync` sampai backend solution melakukan [sinkronisasi](#_3-sinkronisasi-permission)).
   Tombol salin di samping kode memudahkan membagikannya ke tim solution.

   ![Halaman ringkasan solution](/images/docs/onboarding-solution/04-detail.png)

Solution yang dibuat lewat console langsung berstatus `active`. Untuk menonaktifkannya, pakai kartu
**Nonaktifkan solution** di tab yang sama. Console meminta Anda mengetik kode solution sebagai konfirmasi.

### Lewat API

```bash
curl -X POST "$PLATFORM/api/v1/solutions" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "code": "kasir-pintar",
    "name": "Kasir Pintar",
    "description": "Aplikasi kasir (POS) untuk toko retail.",
    "status": "active"
  }'
```

Respons `201`:

```json
{
  "status": "success",
  "status_code": 201,
  "data": {
    "id": "954dcaaf-...",
    "code": "kasir-pintar",
    "name": "Kasir Pintar",
    "description": "Aplikasi kasir (POS) untuk toko retail.",
    "status": "active",
    "permission_catalog_version": null,
    "created_at": "2026-10-30T08:00:00Z",
    "updated_at": "2026-10-30T08:00:00Z"
  }
}
```

- `code` **tidak bisa diubah** setelah dibuat. Frontend solution mengirim nilai ini saat login
  (`"solution": "kasir-pintar"`), dan nilai ini menjadi `aud` token user.
- Simpan `id`, karena dipakai di path seperti `/solutions/{solutionId}/permissions`.
- Solution `inactive` tidak bisa dipakai login, dan token service-nya ditolak.
- Ubah nama/deskripsi/status: `PATCH /api/v1/solutions/{solutionId}`.

::note
Pada deployment `on_prem`, data solution dikelola lewat license, sehingga `POST /solutions` dan
`PATCH /solutions/{id}` mengembalikan `403 LICENSE_MANAGED`.
::

## 2. Buat solution client

Solution client adalah kredensial backend solution (`client_id` + `client_secret`) untuk mendapat
[token service](/docs/service-token). Buat satu client per lingkungan (mis. production dan staging).

### Lewat console

1. Di halaman solution, buka tab **Client**, lalu klik **Buat client**.

   ![Tab Client yang masih kosong](/images/docs/onboarding-solution/05-clients.png)

2. Isi **Nama**, sebaiknya dengan lingkungan dan fungsinya (mis. `Kasir Pintar Backend Prod`). Pilih
   **Scope** dari daftar. Setiap scope punya keterangan singkat; pilih hanya scope yang dibutuhkan
   (lihat [Memilih scope](#memilih-scope)).

   ![Daftar pilihan scope](/images/docs/onboarding-solution/06-client-scopes.png)

3. Klik **Buat client**.

   ![Form buat client terisi](/images/docs/onboarding-solution/06-client-create.png)

4. Console menampilkan `client_id` dan `client_secret`. **Secret hanya ditampilkan sekali.** Salin
   keduanya ke secret manager backend solution, centang **Saya sudah menyimpan secret ini di tempat aman**,
   lalu klik **Selesai**. Modal ini tidak bisa ditutup sebelum kotak tersebut dicentang.

   ![Modal secret client yang hanya tampil sekali](/images/docs/onboarding-solution/07-secret.png)

5. Client muncul di daftar. Kolom **Terakhir dipakai** terisi setelah backend menukar token pertama kali.
   Menu **⋮** di setiap baris berisi **Ubah nama & scope**, **Rotate secret**, dan **Revoke**.

   ![Daftar client](/images/docs/onboarding-solution/08-client-list.png)

### Lewat API

```bash
curl -X POST "$PLATFORM/api/v1/solutions/$SOLUTION_ID/clients" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Kasir Pintar Backend Prod",
    "scopes": ["users:read", "users:write", "org:read", "org:write", "roles:write", "authz:check", "catalog:sync"]
  }'
```

Respons `201`:

```json
{
  "data": {
    "id": "b3a7...",
    "solution_id": "954dcaaf-...",
    "name": "Kasir Pintar Backend Prod",
    "client_id": "cli_8d0f2c9a41b7e03d5c6f1a28",
    "client_secret": "Qk3vX9...(base64url, 43 karakter)",
    "scopes": ["users:read", "users:write", "org:read", "org:write", "roles:write", "authz:check", "catalog:sync"],
    "status": "active",
    "last_used_at": null,
    "revoked_at": null
  }
}
```

::warning
`client_secret` **hanya ditampilkan sekali** di respons ini. Platform hanya menyimpan hash-nya.
Simpan secret di secret manager backend solution, jangan di frontend atau repository.
::

### Memilih scope

Berikan scope seminimal mungkin. Scope yang relevan untuk fase ini:

| Scope | Untuk |
|---|---|
| `users:read` | Membaca company, member, summary |
| `users:write` | Menambah / mengubah / mengeluarkan member |
| `org:read` | Membaca branch |
| `org:write` | Mengubah company, membuat / mengubah / menghapus branch |
| `roles:write` | Mengelola role custom company dan role assignment |
| `authz:check` | `authz/check`, `check-batch`, `effective-permissions` |
| `catalog:sync` | Sinkronisasi katalog permission solution |

Scope `entitlements:read`, `usage:write`, `events:read`, dan `license:read` tersedia tapi belum relevan
(lihat [Pengantar](/docs#status-fitur)).

### Mengelola client

| Aksi | Console (menu ⋮) | Endpoint |
|---|---|---|
| Daftar client | Tab **Client** | `GET /api/v1/solutions/{solutionId}/clients` |
| Detail | — | `GET /api/v1/solution-clients/{clientId}` |
| Ubah nama / scope | **Ubah nama & scope** | `PATCH /api/v1/solution-clients/{clientId}`. `scopes` menggantikan seluruh scope |
| Rotate secret | **Rotate secret** | `POST /api/v1/solution-clients/{clientId}/rotate-secret`. Secret baru tampil sekali, secret lama langsung tidak berlaku |
| Revoke | **Revoke** (ketik nama client untuk konfirmasi) | `POST /api/v1/solution-clients/{clientId}/revoke`. Permanen |

`{clientId}` di path adalah `id` (UUID), bukan `client_id`.

Pengurangan scope dan revoke **langsung berlaku** untuk token yang sudah terbit, karena platform
memvalidasi ulang token service di setiap request.

**Rotasi tanpa downtime:** buat client kedua, deploy backend dengan kredensial baru, lalu revoke client lama.

## 3. Sinkronisasi permission

Permission didefinisikan oleh solution, bukan oleh platform. Langkah ini dijalankan **backend solution**
memakai client dari langkah 2 (scope `catalog:sync`), idealnya otomatis setiap deploy. Console tidak
menyediakan form untuk mengubah katalog.

```bash
# 1) Tukar kredensial client menjadi token service
SERVICE_TOKEN=$(curl -s -X POST "$PLATFORM/api/v1/oauth/token" \
  -d "grant_type=client_credentials" \
  -d "client_id=$CLIENT_ID" \
  -d "client_secret=$CLIENT_SECRET" \
  -d "scope=catalog:sync" | jq -r .access_token)

# 2) Kirim seluruh katalog permission solution
curl -X PUT "$PLATFORM/api/v1/solutions/$SOLUTION_ID/permissions/sync" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "version": "2026.10.30-1",
    "permissions": [
      { "code": "sale.create",    "name": "Buat transaksi penjualan" },
      { "code": "sale.read",      "name": "Lihat transaksi" },
      { "code": "sale.void",      "name": "Batalkan transaksi", "description": "Membatalkan transaksi yang sudah dibayar" },
      { "code": "product.read",   "name": "Lihat produk" },
      { "code": "product.manage", "name": "Kelola produk & harga" },
      { "code": "report.read",    "name": "Lihat laporan penjualan" },
      { "code": "shift.manage",   "name": "Buka & tutup shift kasir" }
    ]
  }'
```

Detail format, perilaku, dan respons ada di [Sinkronisasi permission](/docs/permission-sync).

### Memeriksa hasilnya di console

Buka tab **Permission** di halaman solution. Halaman ini hanya-baca dan menampilkan katalog terakhir yang
dikirim backend. Bisa dicari berdasarkan kode/nama atau difilter status (`active` / `deprecated`).
Versi katalog di tab **Ringkasan** ikut berubah sesuai `version` yang dikirim.

![Tab Permission berisi katalog hasil sync](/images/docs/onboarding-solution/10-permissions.png)

API: `GET /api/v1/solutions/{solutionId}/permissions`.

## 4. Siapkan role global (opsional)

Role global adalah template role yang tersedia di **semua company** yang memakai solution, mis. `kasir`,
`supervisor`, atau `viewer`. Company tetap bisa membuat role custom sendiri (lihat
[Onboarding company](/docs/onboarding-company#_6-buat-role-custom)). Role hanya bisa berisi permission yang sudah
disinkronkan, jadi jalankan langkah 3 lebih dulu.

### Lewat console

1. Buka tab **Role global**, klik **Buat role global**. Isi **Nama**; **Kode** terisi otomatis dan tidak bisa
   diubah setelah dibuat. Isi **Deskripsi** bila perlu. Opsi **Salin permission dari** dapat dipakai untuk
   mulai dari permission role lain. Klik **Buat role**.

   ![Form buat role global](/images/docs/onboarding-solution/11-role-create.png)

2. Console membuka halaman role. Permission dikelompokkan per prefix kode (mis. `sale.*` → **Sale**).
   Centang permission yang diperlukan, atau centang kotak di judul grup untuk memilih semuanya. Bar di bawah
   menampilkan jumlah perubahan; klik **Simpan permission**.

   ![Memilih permission role global](/images/docs/onboarding-solution/12-role-permissions.png)

### Lewat API

```bash
# Buat role global
curl -X POST "$PLATFORM/api/v1/solutions/$SOLUTION_ID/roles" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"code": "kasir", "name": "Kasir", "description": "Melayani transaksi penjualan harian."}'

# Atur permission-nya (replace-all)
curl -X PUT "$PLATFORM/api/v1/roles/$ROLE_ID/permissions" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"permission_codes": ["sale.create", "sale.read", "product.read", "shift.manage"]}'
```

Endpoint role lainnya ada di [Role](/docs/role).

## Checklist serah terima ke tim solution

Setelah onboarding, berikan informasi berikut ke tim yang membangun solution:

| Data | Dipakai untuk |
|---|---|
| `code` solution (mis. `kasir-pintar`) | Field `solution` saat [login user](/docs/login-user); nilai `aud` token user |
| `id` solution | Path endpoint per-solution (permission sync, role) |
| `client_id` + `client_secret` | [Token service](/docs/service-token) backend (lewat secret manager, bukan chat/email) |
| Base URL platform | `$PLATFORM` dan JWKS di `/api/v1/.well-known/jwks.json` |
