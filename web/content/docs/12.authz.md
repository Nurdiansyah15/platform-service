## Cara kerja

```text
user ──(member active)──▶ company
  └──(role assignment + scope_values)──▶ role ──(permission @ scope_type)──▶ permission
```

Scope disimpan di dua tempat:

| Di mana | Isi | Contoh |
|---|---|---|
| Permission role (`role_permissions`) | `scope_type` tiap permission: level tempat ia berlaku | `items.read` @ `company`, `profile.view` @ `self` |
| Role assignment | `scope_values`: nilai untuk setiap scope_type non-company yang dipakai role | `{"self": "u-1"}` |

Satu permission role menghasilkan satu **grant** pada scope `scope_type` + nilai dari assignment
(`company` = company assignment itu). User **diizinkan** untuk permission `P` pada scope `S` bila:

1. user adalah member `active` company, **dan**
2. punya grant `P` dari role (milik solution yang dicek) yang mencakup `S`:
   - grant `company` mencakup company itu dan semua scope di bawahnya (branch dan scope custom);
   - grant `branch` mencakup branch itu, plus scope custom ber-parent `branch` yang dicek dengan
     `parent_id` = branch itu;
   - grant scope custom hanya mencakup scope yang sama persis (type + nilai);
   - cek di level company hanya dipenuhi grant level company.

Contoh role **manager** (`items.read` @ company, `profile.view` @ self) diberikan dengan
`{"self": "u-1"}`: `items.read` diizinkan di company, cabang mana pun, dan scope custom mana pun;
`profile.view` hanya diizinkan untuk `self` = `u-1`.

Role yang sudah dihapus tidak dihitung. Permission `deprecated` yang masih terpasang di role tetap dihitung.
Bila role diubah sehingga memakai scope_type yang belum punya nilai di assignment lama, permission
ber-scope itu tidak berlaku untuk assignment tersebut.

## Role assignment

| Method & path | Scope service |
|---|---|
| `GET /api/v1/companies/{companyId}/users/{userId}/role-assignments` | `roles:write` |
| `POST /api/v1/companies/{companyId}/users/{userId}/role-assignments` | `roles:write` |
| `DELETE /api/v1/role-assignments/{assignmentId}` | `roles:write` |

Memberi dan mencabut role dengan token user butuh permission platform `role.assign`:

- level **company**, bila role memberi permission ber-scope `company` atau scope custom;
- level company **atau cabang itu**, bila seluruh permission role ber-scope `branch`.

Role milik solution console (mis. `company_admin`) hanya bisa diberikan atau dicabut oleh pemegang seluruh
permission platform. Lihat [permission platform](/docs/arsitektur-integrasi#permission-platform).

### Memberi role

```bash
curl -X POST "$PLATFORM/api/v1/companies/$COMPANY_ID/users/$USER_ID/role-assignments" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"role_id": "5e0b...", "scope_values": {"branch": "a81e...", "department": "42"}, "scope_labels": {"department": "Keuangan"}}'
```

### Nilai scope

- `scope_values` wajib berisi **tepat** satu nilai untuk setiap scope_type non-company yang dipakai
  permission role (lihat `scope_type` di `GET /roles/{roleId}/permissions`). Role yang seluruh permission-nya
  ber-scope `company` cukup `{"role_id": "..."}`.
- `branch` = ID cabang milik company. Scope custom = ID milik solution (string bebas, maks 150); platform
  tidak memvalidasi keberadaannya — itu data solution. Scope type harus terdaftar & aktif
  (`GET /api/v1/solutions/{solutionId}/scope-types`).
- `scope_labels` opsional, hanya untuk scope custom — nama tampilan di daftar assignment.
- Role yang sama untuk nilai berbeda (mis. manager di cabang A dan cabang B) = assignment terpisah.

Respons `201`:

```json
{
  "data": {
    "id": "91b2...",
    "company_id": "7d2e4c10-...",
    "user_id": "3c4d...",
    "role_id": "5e0b...",
    "role_code": "hr-manager",
    "solution_id": "6f1c0a52-...",
    "scope_values": { "branch": "a81e...", "department": "42" },
    "scope_labels": { "department": "Keuangan" },
    "created_at": "..."
  }
}
```

| Kondisi | Respons |
|---|---|
| User bukan member `active` company | `422` |
| Role tidak ada / dihapus / custom milik company lain / (token service) milik solution lain | `422` |
| Nilai untuk scope_type yang dipakai role tidak dikirim / kosong | `422` |
| `scope_values` / `scope_labels` memuat scope_type yang tidak dipakai role | `422` |
| Cabang bukan milik company, atau scope type custom tidak dikenal / `deprecated` | `422` |
| Role + nilai scope yang sama sudah di-assign | `409` |

### Melihat & mencabut

```bash
curl "$PLATFORM/api/v1/companies/$COMPANY_ID/users/$USER_ID/role-assignments?solution_id=$SOLUTION_ID" \
  -H "Authorization: Bearer $TOKEN"
```

Setiap item berisi `role_code`, `role_name`, `role_is_global`, `solution_code`, `scope_values`,
`scope_labels`, dan `scopes` — `[{type, type_name, value, name}]` untuk ditampilkan (nama cabang, label, atau
nilai). Token service hanya melihat role solution-nya; token user boleh memfilter dengan
`solution_id` (tanpa filter = semua solution).

```bash
curl -X DELETE "$PLATFORM/api/v1/role-assignments/$ASSIGNMENT_ID" -H "Authorization: Bearer $TOKEN"
```

Assignment milik company yang tidak bisa diakses, atau (token service) role solution lain → `404`.

## Cek permission

Butuh token user atau token service ber-scope `authz:check`.

### Siapa yang dicek

| Token | `company_id`, `user_id` | Solution yang dicek |
|---|---|---|
| Service | **Wajib** diisi | Solution milik client |
| User | Opsional; bila diisi harus sama dengan `cid` dan user token sendiri | Solution `aud` token |

Token user hanya bisa mengecek **dirinya sendiri** di company aktif. Untuk mengecek user lain, gunakan
token service.

### Satu permission

```bash
curl -X POST "$PLATFORM/api/v1/authz/check" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "company_id": "7d2e4c10-...",
    "user_id": "3c4d...",
    "permission": "payroll.run",
    "scope_type": "branch",
    "scope_id": "a81e..."
  }'
```

```json
{
  "data": {
    "permission": "payroll.run",
    "scope_type": "branch",
    "scope_id": "a81e...",
    "allowed": true,
    "granted_by": ["hr-manager"]
  }
}
```

`scope_type` default `company`. `granted_by` berisi code role yang memberi izin (kosong bila ditolak).

Untuk scope custom ber-parent `branch`, sertakan `parent_id` (ID branch induk) agar grant ber-scope
cabang itu ikut berlaku:

```json
{ "company_id": "...", "user_id": "...", "permission": "leave.approve",
  "scope_type": "department", "scope_id": "42", "parent_id": "a81e..." }
```

### Banyak permission sekaligus

Maksimal 100 cek per request, untuk satu user & company:

```bash
curl -X POST "$PLATFORM/api/v1/authz/check-batch" \
  -H "Authorization: Bearer $SERVICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "company_id": "7d2e4c10-...",
    "user_id": "3c4d...",
    "checks": [
      { "permission": "employee.read" },
      { "permission": "payroll.run", "scope_type": "branch", "scope_id": "a81e..." }
    ]
  }'
```

```json
{
  "data": {
    "company_id": "7d2e4c10-...",
    "user_id": "3c4d...",
    "results": [
      { "permission": "employee.read", "scope_type": "company", "scope_id": "7d2e4c10-...", "allowed": false, "granted_by": [] },
      { "permission": "payroll.run", "scope_type": "branch", "scope_id": "a81e...", "allowed": true, "granted_by": ["hr-manager"] }
    ]
  }
}
```

Semua scope divalidasi lebih dulu: satu `scope_id` / `scope_type` / `parent_id` yang salah membuat
seluruh request ditolak (`422`). Scope type custom yang sudah `deprecated` tetap boleh dicek.

- Permission yang tidak dikenal **tidak** error — hasilnya `allowed: false`.
- User bukan member `active` → semua `allowed: false`.

### Semua permission user

Untuk membangun menu/UI sekaligus:

```bash
curl "$PLATFORM/api/v1/companies/$COMPANY_ID/users/$USER_ID/effective-permissions?solution_id=$SOLUTION_ID" \
  -H "Authorization: Bearer $TOKEN"
```

```json
{
  "data": [
    {
      "permission": "payroll.run",
      "name": "Jalankan payroll",
      "group": { "code": "payroll", "name": "Payroll", "sort_order": 1 },
      "grants": [
        { "role_code": "hr-manager", "scope_type": "branch", "scope_id": "a81e..." }
      ]
    }
  ]
}
```

Token user wajib mengisi `solution_id` (ambil dari `session.solution.id` di `GET /auth/me`); token
service otomatis memakai solution-nya. User bukan member
`active` → daftar kosong.

## Pola integrasi yang disarankan

**Frontend** — setelah switch company, ambil `effective-permissions` sekali untuk menampilkan / menyembunyikan
menu. Ini hanya untuk tampilan, bukan pengaman.

**Backend** — tegakkan izin di setiap aksi penting dengan `authz/check` atau `check-batch` memakai
token service:

```go
// pseudo-code middleware backend solution
claims := verifyUserToken(r)                     // sub, cid dari JWT (lihat halaman Token)
ok := platform.Check(ctx, CheckRequest{
    CompanyID:  claims.Cid,
    UserID:     claims.Sub,
    Permission: "payroll.run",
    ScopeType:  "branch",
    ScopeID:    branchID,
})
if !ok.Allowed { return 403 }
```

**Caching** — hasil check boleh di-cache singkat (mis. 30–60 detik) per `(company, user, permission, scope)`
untuk mengurangi latensi. Perubahan role/member baru terlihat setelah cache habis; jangan cache lama untuk
aksi sensitif.
