Halaman ini untuk tim yang sebelumnya menjalankan solution sebagai aplikasi penuh, dengan user, login,
role, dan cek izin sendiri. Setelah integrasi, urusan itu dipegang platform. Solution cukup menyimpan data
bisnisnya dan meminta platform setiap kali butuh identitas, data organisasi, atau keputusan izin.

```text
                 token user (aud = kode solution, cid)
 FE solution ─────────────────────────────────────────▶ BE solution ── token user / service ──▶ Platform
   │  SSO / login, refresh, /auth/me, /auth/apps            │  1. verifikasi JWT (JWKS)
   │  (boleh langsung ke platform)                          │  2. authz/check (token service)
   └────────────────────────────────────────────────────────┤  3. data bisnis di DB solution
                                                            │  4. ubah data organisasi (teruskan token user)
```

## Siapa memegang apa

| Hal | Dulu (aplikasi mandiri) | Sekarang |
|---|---|---|
| Akun user, password, login | Tabel `users` + form login solution | Platform. Login lewat [SSO dari console](/docs/sso-console). |
| Company / tenant, cabang | Tabel solution | Platform (`company_id`, `branch_id`) |
| Anggota company | Tabel solution | Platform (`company_members`) |
| Role & permission | Tabel solution | Platform. Katalog permission tetap ditulis solution lewat [sync](/docs/permission-sync). |
| Cek izin | Kode solution | `POST /authz/check` di platform |
| Data bisnis (transaksi, produk, laporan, …) | DB solution | **Tetap di DB solution**, dengan kunci ID dari platform |

Di DB solution, simpan **ID** dari platform (`company_id`, `branch_id`, `user_id`) sebagai kolom biasa,
tanpa foreign key ke tabel lokal. Nama user dan nama cabang **tidak** perlu disalin. Ambil saat dibutuhkan
dari platform, lalu cache sebentar (mis. 5 menit).

```sql
-- contoh tabel bisnis di DB solution
CREATE TABLE sales (
  id          UUID PRIMARY KEY,
  company_id  UUID NOT NULL,  -- dari platform
  branch_id   UUID NOT NULL,  -- dari platform
  cashier_id  UUID NOT NULL,  -- user_id dari platform
  total       NUMERIC(14,2) NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Frontend (FE)

1. **Masuk.** Pakai [SSO dari console](/docs/sso-console), atau [login password](/docs/login-user) untuk
   aplikasi mobile. Hasilnya token user dengan `aud` = kode solution dan `cid` = company aktif.
2. **Panggil BE solution** dengan header `Authorization: Bearer <access_token>`.
3. **Langsung ke platform hanya untuk urusan sesi dan identitas.** Contohnya `/auth/me`, `/auth/refresh`,
   `/auth/companies`, `/auth/switch-company`, dan `/auth/apps` untuk [menu apps](/docs/sso-console#_3-menu-apps-di-navbar-solution).
4. **Tampilkan atau sembunyikan menu** berdasarkan `GET /companies/{cid}/users/{uid}/effective-permissions`.
   Ini hanya untuk tampilan; penegakan izin tetap di BE.

## Backend (BE)

### 1. Verifikasi token user

Verifikasi JWT secara lokal dengan JWKS platform. Tidak perlu memanggil platform di setiap request.

```go
// Go — github.com/MicahParks/keyfunc/v3 + golang-jwt/v5
jwks, _ := keyfunc.NewDefault([]string{platformURL + "/api/v1/.well-known/jwks.json"})

func Authenticate(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		raw := strings.TrimPrefix(r.Header.Get("Authorization"), "Bearer ")
		claims := jwt.MapClaims{}
		_, err := jwt.ParseWithClaims(raw, claims, jwks.Keyfunc,
			jwt.WithIssuer(platformURL), jwt.WithAudience("kasir-pintar"), jwt.WithValidMethods([]string{"RS256"}))
		sub, _ := claims["sub"].(string)
		cid, _ := claims["cid"].(string)
		if err != nil || claims["typ"] != "user" || sub == "" || cid == "" {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		ctx := context.WithValue(r.Context(), userKey{}, User{ID: sub, CompanyID: cid, Token: raw})
		next.ServeHTTP(w, r.WithContext(ctx))
	})
}
```

Token yang dicabut, misalnya karena logout atau user di-suspend, tetap lolos verifikasi lokal sampai `exp`
(maks. 15 menit). Untuk aksi sensitif, cek ulang dengan `GET /auth/me` memakai token user, atau andalkan
`authz/check`, yang selalu membaca kondisi terkini. Detail claim ada di [Token](/docs/token).

### 2. Dua token untuk memanggil platform

| Token | Dipakai untuk |
|---|---|
| **Token user** yang diterima dari FE (diteruskan apa adanya) | Mengubah data organisasi **atas nama user**. Platform menegakkan [permission platform](#permission-platform). |
| **[Token service](/docs/service-token)** (client credentials, di-cache sampai hampir habis) | `authz/check` izin bisnis, membaca data organisasi, sync katalog, dan pekerjaan sistem tanpa user (import, job terjadwal). Scope mis. `users:read org:read authz:check catalog:sync`. |

### 3. Cek izin bisnis

Sebelum aksi bisnis, tanyakan platform dengan permission dari katalog solution Anda sendiri:

```go
func (p *Platform) Can(ctx context.Context, u User, perm string, branchID string) (bool, error) {
	body := map[string]any{"company_id": u.CompanyID, "user_id": u.ID, "permission": perm}
	if branchID != "" {
		body["scope_type"], body["scope_id"] = "branch", branchID
	}
	var out struct{ Data struct{ Allowed bool `json:"allowed"` } `json:"data"` }
	err := p.post(ctx, "/api/v1/authz/check", body, &out) // memakai token service
	return out.Data.Allowed, err
}

// handler "batalkan transaksi"
if ok, _ := platform.Can(ctx, user, "sale.void", sale.BranchID); !ok {
	return forbidden()
}
```

Untuk satu halaman yang butuh banyak cek, pakai `POST /authz/check-batch`. Detail ada di [Authz](/docs/authz).

### 4. Mengubah data organisasi

Operasi seperti membuat user, menambah cabang, atau memberi role dijalankan di platform. Siapa pun yang
memanggil, **platform yang menegakkan izinnya** lewat [permission platform](#permission-platform) bila
yang dipakai token user.

| Pola | Alur | Kapan |
|---|---|---|
| **A. BE meneruskan token user (disarankan)** | FE → BE solution → platform dengan token user yang sama | BE perlu logika tambahan, mis. menulis data bisnis terkait atau audit log |
| **B. FE langsung** | FE → platform dengan token user | Form sederhana tanpa logika tambahan |
| **C. Token service** | BE → platform dengan token service | Hanya pekerjaan **sistem** tanpa user (import awal, sinkronisasi). Platform **tidak** mengecek permission platform untuk token service, jadi jangan pakai untuk aksi yang dipicu user. |

```go
// Tambah cabang lewat BE (pola A): token user diteruskan, platform yang menolak bila tanpa branch.manage.
func (h *Handler) CreateBranch(w http.ResponseWriter, r *http.Request) {
	u := UserFrom(r.Context())
	branch, status, err := h.platform.WithToken(u.Token).CreateBranch(r.Context(), u.CompanyID, req)
	if status == http.StatusForbidden {
		http.Error(w, "forbidden", http.StatusForbidden) // teruskan pesan errors dari platform ke FE
		return
	}
	// ... simpan data bisnis terkait cabang di DB solution
}
```

## Permission platform

Administrasi company dijaga lima permission bawaan. Pembuat company otomatis mendapat role **`company_admin`**
(Admin company) yang berisi kelimanya.

| Operasi | Endpoint | Permission platform (token user) | Scope token service |
|---|---|---|---|
| Buat akun user + jadikan anggota | `POST /companies/{cid}/users` | `member.manage` | `users:write` |
| Tambah / ubah status / keluarkan anggota | `POST /companies/{cid}/members`, `PATCH`/`DELETE /companies/{cid}/members/{uid}` | `member.manage` | `users:write` |
| Ubah nama / slug company | `PATCH /companies/{cid}` | `company.manage` | `org:write` |
| Tambah cabang | `POST /companies/{cid}/branches` | `branch.manage` (level company) | `org:write` |
| Ubah / hapus cabang | `PATCH`/`DELETE /branches/{branchId}` | `branch.manage` (level company **atau** cabang itu) | `org:write` |
| Buat / ubah / hapus role custom, atur permission-nya | `/companies/{cid}/solutions/{sid}/roles`, `/companies/{cid}/roles/{rid}…` | `role.manage` | `roles:write` |
| Beri / cabut role | `POST /companies/{cid}/users/{uid}/role-assignments`, `DELETE /role-assignments/{id}` | `role.assign` (pada scope assignment) | `roles:write` |

- Endpoint **baca** (daftar anggota, cabang, role) tetap terbuka untuk semua anggota aktif.
- Platform admin dan token service tidak dicek permission platform-nya (lihat pola C di atas).
- Company bisa membuat role custom di solution console untuk kombinasi yang lebih sempit. Contoh: role
  "Kepala Cabang" berisi `branch.manage` + `role.assign`, di-assign pada scope cabang. Pemegangnya bisa
  mengubah cabangnya sendiri dan memberi role di cabang itu saja.
- **Anti eskalasi:** role milik solution console (berisi permission platform) hanya bisa dibuat, diubah,
  diberikan, atau dicabut oleh user yang memegang **seluruh** permission platform pada scope tersebut.
  Pemegang `role.assign` saja tidak bisa menjadikan dirinya `company_admin`.

Ditolak → `403` dengan pesan *"Anda tidak punya izin mengelola company ini …"*.

## Contoh per operasi

```bash
# Buat user (akun + password awal) sekaligus jadikan anggota company
curl -X POST "$PLATFORM/api/v1/companies/$CID/users" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "Rudi Hartono", "email": "rudi@majujaya.co.id", "password": "Sementara#2026"}'
# 201 → { "data": { "user_id": "…", "email": "…", "status": "active", … } }
# 409 bila email sudah terdaftar → tambahkan sebagai anggota:
curl -X POST "$PLATFORM/api/v1/companies/$CID/members" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"email": "rudi@majujaya.co.id"}'

# Ubah info company
curl -X PATCH "$PLATFORM/api/v1/companies/$CID" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"name": "PT Maju Jaya Abadi"}'

# Tambah & ubah cabang
curl -X POST "$PLATFORM/api/v1/companies/$CID/branches" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"name": "Cabang Bogor", "code": "BGR"}'
curl -X PATCH "$PLATFORM/api/v1/branches/$BRANCH_ID" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"name": "Cabang Bogor Kota"}'

# Buat role custom solution Anda + atur permission
curl -X POST "$PLATFORM/api/v1/companies/$CID/solutions/$SOLUTION_ID/roles" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"code": "kasir_senior", "name": "Kasir Senior"}'
curl -X PUT "$PLATFORM/api/v1/companies/$CID/roles/$ROLE_ID/permissions" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"permission_codes": ["sale.create", "sale.read", "sale.void"]}'

# Beri role ke anggota di satu cabang
curl -X POST "$PLATFORM/api/v1/companies/$CID/users/$USER_ID/role-assignments" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" -d '{"role_id": "'$ROLE_ID'", "scope_type": "branch", "scope_id": "'$BRANCH_ID'"}'
```

`$TOKEN` adalah token user (pola A/B), atau token service untuk pekerjaan sistem (pola C). Referensi lengkapnya ada di
[Company, member & branch](/docs/company-member-branch), [Role](/docs/role), dan [Authz](/docs/authz).

## Migrasi dari auth/authz lama

1. **Katalog permission.** Petakan izin lama ke kode permission (`sale.void`, `report.read`, …), lalu
   jalankan [sync](/docs/permission-sync) saat deploy.
2. **Company & cabang.** Buat company (`POST /companies`) dan cabang. Simpan pemetaan ID lama → ID platform,
   lalu ganti kolom tenant/cabang di tabel bisnis menjadi ID platform.
3. **User.** Untuk setiap user lama, panggil `POST /companies/{cid}/users` dengan password awal (token
   service, scope `users:write`). Bila
   `409`, user sudah ada (mis. dari solution lain), jadi tambahkan sebagai anggota. Hash password lama
   tidak bisa dibawa; minta user mengganti password setelah login pertama.
4. **Role.** Buat role custom per company, atau minta platform admin membuat role global. Isi
   permission-nya, lalu assign ke anggota dengan scope yang sama dengan sistem lama.
5. **Admin company.** Pastikan minimal satu anggota tiap company memegang `company_admin`. Platform admin
   bisa memberikannya dari console (**Tambah anggota → Jadikan admin company**).
6. **Kode lama.** Ganti form login dengan SSO, ganti cek izin lokal dengan `authz/check`, lalu hapus tabel
   user, role, dan permission lama setelah masa transisi.
